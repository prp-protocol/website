C04-PN: Pending

Rationale

The previous pre-HS2 discovery trace now has isolated execution evidence. The exact unmodified discovery packet handler, queued worker and wire encoder were extracted from the pinned source after SHA-256 verification and compiled with synthetic kernel primitives. Eighteen input cases establish response-sink invocation with the supplied nonce for a public SOLICIT and its repetition, rejection of malformed fields/source MACs/length or disallowed interface, and rejection of new input after discovery is disabled. Work queued before disabling still invokes the response sink; changing link permission before draining the queue blocks that response because the worker rechecks link policy. No identity credential is supplied or consulted by this exercised path. The harness uses a single queued work item, deterministic device/attachment fixtures and a TX sink instead of the original transmitter; it does not establish actual wire delivery, realistic scheduling, cryptographic behavior, timing indistinguishability or the full native 0x0101 listener. The disable option remains available and the rest of the selected stack remains unqualified, so the cell stays Pending rather than converting this bounded result into a global No or Yes.

Assessment method

Exact pinned C parser/worker/encoder compiled and executed with explicit kernel shims; 18 input cases

Source context

prp-linux-kmod fa2f8290 Ethernet carrier and UAPI layout; source hashes pinned in round143

Outstanding qualification

Round144 executed the exact pinned Ethernet discovery parser, worker and encoder with kernel shims and a TX sink: 18 input cases passed, including unauthenticated response invocation, repeated input, disabled ingress and queued-after-disable behavior. This does not run the kernel, real transmitter or scheduler concurrency. Establish a settled disabled-discovery native 0x0101 configuration, then qualify ordinary carrier/admission/HS2 paths and replies/timing against a control endpoint. Keep UDP separate.
