C06-MT: Yes

Rationale

Use independent full native meshtasticd/Portduino contexts with real LoRa radios and separately provisioned state. getMacAddr accepts General.MACAddress before falling back to a host hardware address. Consequently the MAC copied into owner and serialized in NodeInfo need not be a compulsory common hardware identifier. Give each context a distinct explicit MAC, fresh PKI keys/derived node number, independent names and preferences, and no reused location or other identifying telemetry. The generated User schema still serializes macaddr despite its deprecated comment: changing only the PKI key is insufficient on a fixed-MAC setup. This bounded configuration removes the identified mandatory cross-context field link; it is not automatic identity rotation, session continuity, a guarantee for embedded boards, or protection against known attachment/timing inference. Native LoRa is selected; no UDP mesh or Internet bridge is added.

Assessment method

Pinned source analysis and explicit native-platform configuration witness; no RF capture

Source context

Meshtastic native Portduino MAC selection, NodeDB identity setup and generated User schema

Outstanding qualification

Run two clean isolated native contexts with distinct explicit MACAddress values and independent keys/names/state, retaining the selected private-channel/STRICT policy. Verify effective configuration after all hardware/autoconfiguration merges, capture full NodeInfo and routing headers, and inspect trusted-local-client metadata for reused identifiers. Do not reuse stored contacts, device IDs, identifying payloads or GPS telemetry between contexts. Use real LoRa and verify no network-radio fallback. No execution or capture performed.
