D04-RA: No

Rationale

No for the selected IRATI direct application API at the pinned revision. Dynamic application naming is present: registration supplies a name to an already assigned IPCP and does not allocate an interface address per name. However, rina_register_common opens another control descriptor through rina_open and irati_open_ctrl_port, which opens the shared control device read/write. The decisive additional trace is kernel/kipcm.c: the same dispatch table registers create-IPCP, destroy-IPCP and assign-to-DIF commands. ctrldev_write dispatches caller-selected kernel message types without an implemented permission check. The corresponding handlers invoke kipcm_ipc_create, kipcm_ipc_destroy or the IPCP assignment operation without checking the caller against a management principal. The sender control port is used for the response, not an authorization check. Therefore granting the direct device access required by registration also grants access to network-management operations. Denying that access blocks this API. This concrete authority coupling fails D04's requirement that additional identities be usable by an ordinary user without network-administration authority; it is not an inference from a failed search for documentation.

Assessment method

Static end-to-end authority trace; no runtime or exploit execution

Source context

Pinned IRATI registration API, control-device dispatch and concrete kernel management handlers

Outstanding qualification

Scope is the selected IRATI/Linux direct API and pinned source, not an impossibility theorem about RINA or a claim about every implementation. An actual restricted broker, kernel authorization boundary or supported confinement policy could change this result; none is added implicitly to the selected composition. Merely granting a device group or running the API under a non-root UID does not restrict the operations exposed by that descriptor. No malicious command, exploit or runtime test was executed, and no deployed system is asserted vulnerable. This finding does not erase dynamic naming, require a new address per application, equate an application name with the IPCP authentication key, or change D01/F21. Peer acceptance and prior transport provisioning remain separate. Assessment concerns granted authority, not incidental resource contention or an assumption that the user will exercise management commands.
