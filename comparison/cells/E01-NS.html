E01-NS: Yes

Rationale

The public nostr-bench report dated 2025-12-16 names a Zig client and distinct Strfry (C++) and nostr-rs-relay (Rust) relay implementations, and reports successful event publication exchanges. The report identifies nostr-bench v0.1.1; its retained tag 3b7848a pins libnostr-z v0.1.5. In that tag, the generator signs kind-1 events and the burst-publishing loop sends EVENT and records success only after parsing an OK response with success=true. This documents actual reported NIP-01 client-to-relay traffic between separately developed client and relay cores. Credit that publication/acknowledgment function only, consistent with E01 bounded-function evidence.

Assessment method

Documentary report plus test-assertion review; restricted NIP-01 function credit

Source context

Published Nostr test report and inspected historical client tag with native Zig event signing and relay ACK handling

Outstanding qualification

Public implementer report, not a new execution or packet capture. The client and relays implement complementary NIP-01 roles; this does not claim relay-to-relay federation or synchronization. Relay builds are not pinned exactly: compose uses Strfry latest and the Rust Dockerfile selects the newest available tag at build time. The retained current report and historical client tag do not reconstruct all historical binaries. The benchmark uses ws:// rather than selected WSS/TLS 1.3, and does not qualify concurrent two-relay delivery, reader signature verification, memory-only operator policy or the complete column. A null receive can escape success/error accounting, and the burst loop does not match the OK event ID; do not interpret its displayed 100% as proof that every requested event was accepted. Query, retrieval and NIP-50 results are not credited. No independent performance, security, full compliance or production-duration conclusion follows.
